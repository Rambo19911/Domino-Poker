## Purpose

Domino Poker is an npm-workspace TypeScript monorepo for a browser-playable Domino Poker game.

It has two game modes:

- Single-player: browser-only local game, one human against three CPU players.
- Multiplayer: authoritative real-time server over WebSocket, with lobby rooms, chat, reconnect/resume, turn timers, optional accounts/profiles, SQLite persistence by default, and PostgreSQL persistence/fanout foundations for multi-instance deployments.

The core rule engine is shared. The browser may derive UI hints from shared logic, but authoritative multiplayer decisions belong to the server.

A virtual gold-coin economy is being added on top of the optional account system (server-authoritative). Each registered account holds a coin balance persisted in the DB; single-player wins award coins via a server-issued one-time game token (Phase 2, shipped), and multiplayer paid rooms (host-set entry fee, prize pot split 70/30 to the top-2 registered humans) are shipped server-side (Phase 3) with the paid-room web UI in Phase 4 (fee input gated to logged-in hosts, coin badges in room lists, pot at the table, live `WALLET_UPDATED` balance). Anonymous play is unaffected — anonymous users have no wallet, cannot join paid rooms, and earn nothing. The rules dialogs explain the economy: the main lobby `RulesDialog` has a gold-coin section (welcome bonus + SP rewards), and the MP rules (`lib/mpRulesContent.ts` plus `lib/locales/mpRules/*`) have paid-room sections (entry fee, refund-before-start, 70/30 pot) across all 21 UI locales. Flat UI string parity is TypeScript-enforced through `AppStrings`; MP rules document structure is kept parallel by convention/tests.

## In-Game Store (Cosmetics) And Themes

On top of the gold economy there is an in-game cosmetics store: a coin SINK (not pay-to-win, no real money). It sells 6 purchasable animated-background THEMES (slugs `twilight`, `rain`, `pop-out`, `confetti`, `bubbles`, `luminous`) at a single `THEME_PRICE` (200k, in `packages/shared/src/economy.ts`); `packages/shared/src/store-catalog.ts` is the authoritative item+price catalog imported by both server (validates the itemId + price at purchase) and web (shows price/lock). Ownership is DERIVED from the append-only `coin_ledger` (reason `theme_purchase` for themes / `bot_purchase` for the bot assistant, ref = itemId; `WalletService.listOwnedItems` unions both) — there is no separate inventory table: a purchase is one atomic ledger row that is simultaneously the coin debit AND the ownership grant (exactly-once via `UNIQUE(user_id, reason, ref)`; re-buy is an idempotent no-op = `alreadyOwned`). The server is authoritative (`apps/server/src/store/StoreService.ts` over `WalletService.purchaseItem`/`listOwnedItems`) and exposes `POST /store/buy` + `GET /store/owned` (`apps/server/src/http/storeRoutes.ts`, auth required — anonymous cannot buy; like every new server HTTP route it needs a Caddy `reverse_proxy /store` rule on the VPS or it 404s in prod). The web theme registry (`apps/web/lib/theme.ts`) holds the 7 themes (Default free + 6 paid), gates selectable themes by ownership (`isThemeUnlocked`), and downgrades a stored-but-unowned theme back to Default on auth change (`reconcileStoredTheme`, account-bound enforcement). Each paid theme has its own per-screen palette tokens (`tokens.css`). Animated backgrounds are performance-gated: a pre-paint heuristic (reduced-motion / low `deviceMemory` / low `hardwareConcurrency`) and a post-paint FPS probe (`startMotionFpsProbe`, <40 FPS over ~1.5s) fall back to a static poster via `data-theme-motion="static"`. A CI performance tripwire (`tests/e2e/theme-performance.spec.ts`, opt-in `THEME_PERF=1`) catches catastrophic theme regressions (dead rAF loop, long Long Task, console error) — it is not an FPS gate.

The store also sells a second product kind (`StoreItemKind` `"bot_assistant"`): the "supportHuman" bot assistant "The Sage" for `BOT_ASSISTANT_PRICE` (5M coins, `economy.ts`; item id `SUPPORT_HUMAN_ITEM_ID` = `bot.supportHuman`). `StoreService` maps item `kind -> ledger reason` (theme→`theme_purchase`, bot→`bot_purchase`; the DB `coin_ledger.reason` CHECK was already dropped in 0010, so no migration). The store UI (`apps/web/components/StoreDialog.tsx`, previously a skeleton) is a token-only CSS 3D flip card (inline SVG art, price, Buy/Owned/Login; dense localized description on the back) buying via the same `/store/buy` flow. Once owned, the account gets **3 single-player hints per round** (`HINTS_PER_ROUND`): on the human's turn, `DominoPokerGame` spends a hint and reuses `botBridge.decideMove(state, humanSeat, "epic")` (no new bot engine code) to recommend the best FULL move (tile + declared pip), highlighting it on the hand (`PlayerSeat` hint button on the profile ring + `.recommended` glow + `.hintDeclare` badge; mirrored in `SpMobileTable`). Quota is React state reset per round; the recommendation is cleared on any decision-point change and `tryAdvance`-validated before consuming. **Part B (MP hints) is BUILT (Codex-PASS B1–B3, uncommitted):** new WS pair `REQUEST_HINT` → `HINT_GRANTED`/`HINT_DENIED`; the quota is server-authoritative + ephemeral in `RoomEngine.requestHint`/`syncHintRound` (economy `HINTS_PER_ROUND`, lazy round-reset via `coreState.currentRound`, grants-only idempotence cache keyed `playerId:turnId:requestId` — turnId in the key blocks replaying a grant across turns to bypass the quota); ownership is checked in the ROUTER (`messageRouter.handleRequestHint` via `wallet.listOwnedItems`+`ownsSupportHuman`), NOT in `RoomEngine`. The pure PlayerView conversions were extracted to `apps/web/lib/bot/playerView.ts` (single source, D10) and shared by SP (`botBridge`, core `GameState`) and MP (`apps/web/lib/mp/botView.ts` `buildMpPlayerView`, server `PlayerSnapshot`) — both satisfy the minimal `TrickSourceState`. The MP hint MOVE is computed client-side (D8, `computeMpHint` epic worker); `apps/web/lib/mp/useMpHint.ts` owns the UI state + D9/D11 guards + a synchronous double-spend guard; `useOwnsSupportHuman` gates the button (server still authoritative). Client-side compute bypass is an ACCEPTED, documented risk (owner + Codex, 2026-07-04). See `docs/TODO/support-human-bot-store-plan.md`. Separately, `packages/ai_bot/packages/ai/src/behavior.ts` adds a bot behavior/objective layer (`createBehaviorReward`: `supportHuman`/`denyHuman`/`aggressiveVsHuman`) via a `RewardFn` seam in `ismcts.ts` — built + exported but UNWIRED (the SP hint uses plain inclusion search, not this layer; brand ties, mechanics differ; `docs/bot-behaviors.md`).

## Daily Tasks

A coin FAUCET for registered players: 4 sequential daily tasks (calendar icon in the lobby top bar) that reward gold for winning single-player games by difficulty (win 10 medium / 20 hard / 30 epic / 50 epic → 2000/4000/8000/16000; "win" = SP placement ≤ 2). Progress resets daily at UTC 00:00, accrues in parallel, but claiming is sequential (1→2→3→4 within the same UTC day). Progress is DERIVED from `player_game_results` (a new `countSpWinsSince` over migration `0014`'s additive `duration_ms` column, gated by a per-difficulty min-game-duration anti-abuse constant), and claims are idempotent append-only `coin_ledger` rows (reason `daily_task_reward`, ref `daily:{yyyymmdd}:{taskId}`) — no counter table, no new claim table. Thresholds+rewards live only in `packages/shared/src/economy.ts` (`DAILY_TASKS`; server-enforced). Server: `apps/server/src/daily/DailyTaskService.ts` + `http/dailyTaskRoutes.ts` (`GET /daily/tasks`, `POST /daily/tasks/claim`, auth-required, needs a Caddy `reverse_proxy /daily/*` rule in prod). Web: `apps/web/lib/daily/*` + `components/DailyTasksDialog.tsx`; the calendar icon shows only when logged in and pulses when a reward is claimable. See `docs/TODO/daily-tasks-plan.md`. Residual: SP placement stays client-asserted (same trust as existing SP rewards).

## Weekly Tasks

A second tab in the SAME lobby dialog as Daily Tasks (the calendar icon now opens a tabbed `Daily | Weekly` dialog), for registered players. 4 INDEPENDENT tasks (claim in any order — not sequential like daily), reset every Monday 00:00 UTC, with COUNT-based progress: finish 20 multiplayer games → 40 000; win two standard-room epic 50-round games → 100 000; take a winning place (top-2) in a 30-round SPECIAL room → 150 000; same at 50 rounds → 400 000. The special "weekly bosses" room is a single-player game whose three bots run DIFFERENT behaviors (`inclusion` / `denyHuman` / `aggressiveVsHuman`, all epic) — this is what finally wired the previously-built bot-behavior layer (`docs/bot-behaviors.md`). Those games are tagged `player_game_results.variant = 'weekly_bosses'` (additive migration `0015`), snapshotted server-side from the `/sp/start` token. Progress is DERIVED from `player_game_results` (`countMpFinishedSince` + `countSpTaskWins`), claims are idempotent `coin_ledger` rows (reason `weekly_task_reward`, ref `weekly:{mondayYYYYMMDD}:{taskId}`); thresholds/rewards/rounds live only in `packages/shared/src/economy.ts` (`WEEKLY_TASKS`, server-enforced). Server: `apps/server/src/weekly/WeeklyTaskService.ts` + `http/weeklyTaskRoutes.ts` (`GET /weekly/tasks`, `POST /weekly/tasks/claim`, auth-required, needs a Caddy `reverse_proxy /weekly/*` rule in prod). Web: `apps/web/lib/weekly/*`, the tabbed `DailyTasksDialog.tsx`, and `AppShell.startWeeklyBossRoom` (which launches the special room without overwriting the user's difficulty/round choice). The UTC-Monday launch epoch MUST be a Monday ≤ the current week (a future-Monday value empties the current window — a bug that was found and fixed). Anti-abuse: SP tasks use a round-scaled min-duration gate; the MP task has none by design (small reward). See `docs/TODO/weekly-tasks-plan.md`. Residual: SP placement + variant stay client-asserted (same trust as existing SP rewards).

- npm workspaces.

## Dependency Direction

- `packages/core` is the domain layer. It must not import UI, server, storage, or transport code.
- `packages/core/src/multiplayer` is the deterministic multiplayer state-machine layer around core rules.
- `packages/shared` is the public protocol/DTO layer. It validates external client input and currently depends on core MP types for server snapshots/events.
- `apps/server` is the authoritative application/infrastructure layer for multiplayer. It may use core and shared, and it owns DB/network/time authority.
- Inside `apps/server`, keep request flow directional: gateway/hub -> router -> room manager/engine -> core. Storage, auth, sessions, event bus, and HTTP are infrastructure boundaries around that flow.
- `apps/web` is presentation and client application state. It may use core for single-player and UI hints, and shared for protocol types, but it must not become authoritative for multiplayer decisions.
- Gold-coin economy is server-authoritative: all balance changes flow through `WalletService` over the `CoinStore` boundary (atomic + idempotent ledger). `packages/shared/src/economy.ts` is the one authoritative source for amounts/splits — the server enforces them, the web only displays them. The web never decides balances; it shows `/auth/me` / `WELCOME` values and asks the server to reward/charge.
- `tools/*` are verification/load utilities and must not become production dependencies.
- `packages/ai_bot`: `engine` + `ai` are root npm workspaces consumed by the browser single-player game through `apps/web/lib/bot/botBridge.ts` (maps core `{side1,side2}` tiles <-> bot bitmask `PlayerView`). `ai`'s dep on `engine` is exact `1.0.0` (npm rejects pnpm `workspace:*`). `bot-adapter` (Node `worker_threads`) is intentionally NOT a workspace. Do not keep a local pnpm `node_modules` under `packages/ai_bot` (its `tsc` bin shadows root typescript for the npm build). The browser bridge — not `AiClient` — is the SP integration surface; `bot-adapter`/`AiClient` would only be needed for a Node/Web-Worker transport later.

## Fragile Or High-Risk Areas

- `packages/core/src/gameState.ts`: deal validation, trick winner logic, special 0-6 ace context, round/game scoring, dealer rotation, and tiebreakers.
- `packages/core/src/player.ts`: legal-play validation and scoring. `getInvalidMoveReason` is the structured rule source for UI invalid-move messaging.
- `packages/core/src/dominoTile.ts` and `shuffleAlgorithm.ts`: human-style cut/overhand shuffle is intentional. Do not replace with Fisher-Yates unless explicitly requested.
- `packages/core/src/multiplayer/*`: deterministic seed-driven multiplayer state machine. Do not introduce `Math.random` or `Date.now` into decisions.
- `packages/shared/src/clientMessages.ts`: external input boundary. Keep Zod limits on client-controlled ids, room identifiers, chat text, bids, moves, and pips. `createRoomSchema.entryFee` (Phase 3) is bounded by `MAX_ENTRY_FEE` (sanity cap); the real limit is the host balance, enforced server-side at debit.
- `packages/shared/src/serverEvents.ts`: protocol event/snapshot schemas are coupled to core MP types; changing snapshots/events requires checking core, server, web client, and tests. The `WALLET_UPDATED` event (Phase 3, balance push) and the B-part `HINT_GRANTED`/`HINT_DENIED` events must stay in BOTH the `ServerEvent` union and `serverEventSchema`, or cross-instance Postgres fanout drops them (the web reducer intentionally ignores the hint events — transient RPC handled by `useMpHint`). `RoomSummary.entryFee` + `RoomView.pot` in `roomTypes.ts` are required fields (server always populates; old clients ignore extras).
- `packages/shared/src/economy.ts`: single source for coin amounts/splits — `STARTING_COINS`, `SP_REWARDS`, `POT_SPLIT` (70/30), `MIN_ENTRY_FEE`/`MAX_ENTRY_FEE`, and `splitPot(pot, humanCount)` (remainder→1st, single human→100%). Server enforces; web displays. Do not duplicate these values.
- `packages/shared/src/leaderboard.ts`: single runtime/type source for supported account UI languages (`GAME_LANGUAGES`). Keep it aligned with `apps/web/lib/i18n.ts`; server `PATCH /auth/me/language` validates against this enum, and migration `0013` intentionally removed the DB `CHECK`.
- `apps/server/src/chat/*Translation*` and `apps/server/src/chat/chatTranslateRoutes.ts`: optional MP lobby chat translation. Google credentials must stay in env/secret files, client calls only the server route, and rate/character limits should remain bounded to avoid cost surprises.
- `apps/server/src/net/messageRouter.ts`: large routing/lifecycle file. It enforces membership, ownership, lifecycle finalization, reconnect, and command routing; avoid adding rule logic here. Phase 3 added paid-room money orchestration (the one deliberate exception): `createPaidRoom`/`joinPaidRoom` do debit-then-commit-seat with full rollback (refund + room teardown) on any post-debit failure, and re-check `isUserSeated` synchronously right before the seat commit to close the concurrent duplicate-userId race; leave/delete/TTL refunds go through `tryRefund`, which idempotently credits and, on transient DB failure, queues into `pendingRefunds` (drained by the periodic `sweepExpiredRooms`). Money rules live in `WalletService`/`MatchPayoutService`, not here. The B-part MP hint (`handleRequestHint`) is another deliberate application-layer gate here: membership → room lease → ownership (`wallet.listOwnedItems`+`ownsSupportHuman`, so `RouterWallet` gained `listOwnedItems`) → `RoomManager.requestHint` → engine, then `HINT_GRANTED`/`HINT_DENIED` (denials are events; not-a-member stays ERROR). Ownership belongs here, NOT in `RoomEngine`.
- `apps/server/src/net/WebSocketGateway.ts`, `GatewayHub.ts`, `GatewayConnection.ts`, and `ServerEventBus.ts`: handshake, heartbeat, reconnect, supersede, slow-client backpressure, and cross-instance fanout are tightly coupled. Phase 3 added an optional `isUserBanned` (hard-rejects a banned authed HELLO before WELCOME) and `disconnectUser(userId)` (tears down live authed sessions on ban) — one DB check per handshake, never per message; see the accepted microsecond HELLO↔ban race comment. `wsTransport.ts` checks IP-bans at the HTTP `upgrade` (before the socket is accepted).
- `apps/server/src/sessions/SessionManager.ts`, `DurableSessionStore.ts`, and `apps/server/src/identity/DisplayIdRegistry.ts`: reconnect tokens, display ids, public profiles, and durable cleanup must stay privacy-safe and anonymous-play compatible.
- `apps/server/src/rooms/RoomEngine.ts`: single-writer room state mutation path. Do not mutate room state elsewhere. The B-part MP hint quota (`requestHint`/`syncHintRound`) is an EPHEMERAL per-player counter (`HINTS_PER_ROUND`, lazy round-reset via `coreState.currentRound`) kept OUT of core state (a monetized UI right, not a domino rule) with a grants-only idempotence cache keyed `playerId:turnId:requestId` (turnId in the key is a security guard — without it a client could replay one grant across turns to bypass the quota). `RoomEngine` stays independent of Wallet/storage; ownership is the router's job.
- `apps/server/src/storage/schema.ts`: single DDL source for SQLite and PostgreSQL migrations (latest is `0013_user_preferences_language_open` (relaxes the `user_preferences.language` CHECK from 2 → 21 supported UI languages so language is validated only by the Zod `GAME_LANGUAGES` enum — same DROP-CHECK pattern as `0010`: PG `pg_constraint` DO block, SQLite table rebuild inside `BEGIN IMMEDIATE`/`COMMIT`); then `0012_chat_blocked_words`, `0011_bans` (bans table with `expires_at` + a table-level CHECK `user_id IS NOT NULL OR ip IS NOT NULL`), `0010_coin_ledger_open_reason` (drops the `coin_ledger.reason` CHECK per D6 — dialect-branched: PG `pg_constraint` DO block, SQLite table rebuild inside `BEGIN IMMEDIATE`/`COMMIT` because `migrate()`'s `exec` is not auto-transactional), `0009_admin`, `0008_player_game_results`, `0007_coin_wallet`).
